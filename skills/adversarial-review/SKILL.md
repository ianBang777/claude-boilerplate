# Adversarial Review

만든 세션은 자기 결과를 후하게 본다. 그래서 **공격·판정·반영을 서로 다른 세
역할**이 맡는다. 공격자와 판사는 이 세션의 맥락을 물려받지 않은 새
서브에이전트다.

```
원작자(이 세션) ─ 산출물 ─▶ 공격자 × N (병렬, 서로 다른 각도)
                                │
                                ▼
                              판사 ─ 유효한 비판만 ─▶ 원작자가 반영 · 반박
                                                        │
                                                        ▼
                                                  사용자가 최종 판단
```

한 번만 돈다. 반영 뒤 다시 돌릴지는 사용자가 정한다. 다시 돌릴 때는 직전
결과를 전제 목록에 넣어 같은 지적이 되풀이되지 않게 한다.

## 대상

- 인자로 받은 경로·텍스트. 없으면 이 세션이 마지막으로 만든 산출물. 둘 다
  없거나 경로를 읽을 수 없으면 사용자에게 묻는다.
- 적합: `docs/plans/*.md`, 설계·ADR, 주간 리포트, 템플릿 문구, 커밋·PR 설명,
  분석 결론.
- 부적합: 코드 diff → `/code-review`가 리뷰·검증 파이프라인을 이미 갖고 있다.
  테스트·린트로 판정되는 것 → 그 지표를 먼저 돌린다.

## 절차

### 0. 전제 목록

공격자·판사 모두에게 넘길 것을 먼저 적는다.

- 산출물 전문과 관련 파일 경로.
- 대화에서 **이미 확정된 결정**. "확정 · 공격 제외"라고 표시한다. 공격자는
  대화를 보지 못하므로 이게 없으면 끝난 논의를 다시 공격한다.
- 이 세션의 결론·자기 평가는 **넘기지 않는다.**

### 1. 공격 — Agent × N, 병렬

`fork`가 아니라 **새 에이전트**로 띄운다. fork는 이 세션의 결론까지 물려받아
같은 편이 된다. 모델은 `sonnet`. 흠잡기는 만들기보다 쉽다는 경험칙(펠릭스
리세버그)에 따라 원작자보다 낮은 급도 된다.

각 공격자에게 **다른 각도**를 준다. 같은 지시를 N번 주면 같은 흠을 N번 찾는다.

| # | 각도 | 찾는 것 |
|---|---|---|
| 1 | 사실·근거 | 숫자·인용·파일·API가 실제와 맞나. 확인 가능한 것은 직접 확인한다 |
| 2 | 논리·전제 | 결론이 전제에서 따라 나오나. 전제 자체가 틀렸나. 더 단순한 설명이 있나 |
| 3 | 빠진 것 | 고려하지 않은 시나리오·이해관계자·실패 경로·되돌리기 방법 |
| 4 | 실행 가능성 | 순서·의존성·비용이 현실적인가. 첫 단계부터 막히는 지점 |
| 5 | 독자 | 처음 읽는 사람이 오해하거나 행동하지 못하는 문장 |

기본 각도는 1·2·3. 대상이 계획·배포 순서면 3 대신 4를, 독자에게 그대로 가는
글(템플릿·커밋 메시지)이면 3 대신 5를 쓴다. `--n`으로 늘리면 남은 각도를
번호순으로 더한다.

공격자 프롬프트 골격:

```
아래 산출물이 틀렸다는 것을 증명하라. 각도: <각도>.
파일을 수정하지 않는다. 읽기만 한다.
"확정 · 공격 제외"로 표시된 결정은 공격하지 않는다.
동의하는 부분은 쓰지 않는다. 주장마다
- 위치: 원문 인용
- 무엇이 틀렸나: 한 문장
- 근거: 확인한 파일·출처·재현 (추측이면 "추측"이라고 적는다)
- 심각도: 결론을 뒤집음 / 일부 수정 필요 / 사소
찾지 못하면 "해당 각도에서 유효한 반박 없음"이라고 쓴다. 억지로 만들지 않는다.
```

공격자가 실패하면 N에서 빼고 보고에 적는다. 비판이 0건이면 판사를 띄우지
않는다.

### 2. 판정 — Agent × 1

새 에이전트. 모델은 지정하지 않는다(원작자와 같은 급을 물려받는다). 타당성
판정은 공격만큼 어렵다. 전제 목록과 공격 결과 전부를 넘긴다. 역할은 비판의
**타당성** 판정이지 산출물 재리뷰가 아니다.

```
파일을 수정하지 않는다. 비판의 인용이 원문과 맞는지 확인한다.
각 비판을 유효 / 부분 유효 / 기각으로 판정하고 한 문장으로 이유를 쓴다.
기각 기준: 근거 없는 추측, 원문을 잘못 읽음, 취향 차이, 실행 불가능한 지적,
"확정 · 공격 제외" 결정을 뒤집자는 지적.
같은 지적은 하나로 합치고 출처를 병기한다. 서로 모순되는 비판은 어느 쪽이
맞는지 정하거나 둘 다 기각한다.
유효·부분 유효 목록(심각도순)과 기각 목록(이유 포함)을 둘 다 빠짐없이 낸다.
```

### 3. 반영 — 원작자(이 세션)

판사가 남긴 항목만 받는다. 판사가 유효라 했어도 **원작자는 반박할 수 있다** —
단, 반박은 근거를 적고 보고에 그대로 드러낸다. 반박의 최종 판단은 사용자다.

- 이 세션이 만들었고 아직 사용자가 승인·커밋·게시하지 않은 산출물이면 반영하고
  무엇을 바꿨는지 보고한다.
- 그 외(사용자가 만든 것, 승인된 계획, 커밋·게시된 것)는 수정안을 제시하고
  **확인 후** 반영한다.

## 보고 형식

```markdown
## 적대 리뷰 — <대상>

공격 <N>개 → 비판 <M>건 → 판사 통과 <K>건

| # | 비판 (위치) | 판정 | 처리 |
|---|---|---|---|
| 1 | ... | 유효 | 반영 — <무엇을> |
| 2 | ... | 부분 유효 | 반박 — <근거> |

기각 <M-K>건: <한 줄씩, 왜 기각됐는지>
```

통과한 비판이 거의 없으면 "이 각도들에서는 찾지 못했다"는 뜻이지 산출물이
옳다는 증명이 아니다. 공격이 약했거나 판사가 과하게 걸렀을 수 있으니 기각
목록을 함께 보여 사용자가 확인하게 한다.

## 옵션

```
/adversarial-review docs/plans/foo.md          # 공격 3개(기본)
/adversarial-review --n 5 docs/plans/foo.md    # 각도 5개 전부
```

`--n`은 1~5. 밖이면 거부한다. 결론을 뒤집을 수 있는 큰 결정이나 되돌리기
어려운 배포 계획에만 5까지 올린다.
