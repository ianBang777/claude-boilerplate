# /refine-commits

현재 브랜치가 베이스 브랜치에서 갈라진 이후의 커밋을 **모두 되돌린 뒤**, 같은 변경을
관심사 단위로 다시 묶어 [commit-convention](../commit-convention/SKILL.md) 형식으로
새로 커밋합니다.

목적은 **히스토리 정리**입니다. 작업 중 뒤섞인 커밋(WIP, 수정의 수정, 관심사가 섞인
커밋)을 `git log`에서 한 덩어리로 잘 읽히게 재구성합니다. **코드의 최종 결과물은
1바이트도 바뀌지 않습니다.**

이미 푸시된 브랜치라면 히스토리 재작성이므로 force-push가 필요합니다 — 승인 단계에서
경고합니다.

## 사용법

| 호출 | 동작 |
| --- | --- |
| `/refine-commits` | 베이스 브랜치를 자동 감지하고, 갈라진 지점 이후 커밋을 재구성 |
| `/refine-commits <base>` | 베이스 브랜치를 명시 (예: `/refine-commits develop`) |

## 절대 원칙

**최종 트리가 백업과 100% 동일함을 검증하기 전에는 다음 단계로 넘어가지 않습니다.**

- 재구성은 **메시지·커밋 경계만** 바꾸고 **파일 내용은 절대 바꾸지 않습니다.** 마지막
  검증(`git diff <backup> HEAD`)이 비어 있어야만 성공입니다.
- 각 단계가 실패하면 다음으로 넘어가지 않고, 백업 브랜치를 남긴 채 사용자에게
  보고합니다.
- **백업 브랜치는 이 스킬이 삭제하지 않습니다.** 검증을 통과해도 남기고, 삭제 명령만
  안내합니다 — force-push 전까지는 백업이 유일한 원본입니다.

## 커밋 그룹화 규칙

### 재료와 근거를 분리한다

| 역할 | 출처 |
| --- | --- |
| 커밋에 담을 **내용** | 최종 diff (`<merge-base>..HEAD` + 포함하기로 한 미커밋 변경) |
| 그룹 **경계**를 정하는 근거 | 원본 커밋 이력 (순서·메시지·파일) |

원본 커밋 경계를 무시하지 않습니다. 어떤 변경이 어떤 작업에 속했는지는 원본 이력만
알고 있고, 그 정보는 reset하면 사라집니다. 따라서 **reset 전에 원본 이력을
스냅샷으로 확보**하고, 분할 계획의 각 행에 `출처 커밋`을 표기합니다.

### 판정 순서 (위가 강함)

| # | 규칙 | 내용 |
| --- | --- | --- |
| 1 | **유형 우선** | 단순 스타일·포맷(`style`)은 나중에 한 것이라도 **전부 1커밋**으로 모아 **맨 뒤**에 둔다. 의존성·설정(`chore`)도 같은 취급 |
| 2 | **관심사** | 최종 변경을 기능·영역 단위로 묶는다 (commit-convention 「커밋 분리」와 같은 기준) |
| 3 | **끼임 분리** | 같은 관심사라도, 원본 이력에서 **그 변경들 사이에 다른 관심사 작업이 끼어 있었다면** 별개 커밋으로 나눈다. 한 파일 안이어도 hunk 단위로 나눈다 |
| 4 | **버그 수정** | 아래 「오류 수정」 구분에 따라 분리 또는 흡수 |

규칙 1이 3을 이깁니다 — 스타일 수정은 사이에 무엇이 끼었든 하나로 모읍니다.

규칙 3의 판정 기준은 **시각이 아니라 순서**입니다. 커밋 사이의 시간 간격은 보지
않습니다(점심·퇴근으로 벌어진 간격은 작업 경계가 아닙니다). 원본 커밋 목록을 순서대로
훑어 `A → B → A` 패턴이 보일 때만 두 `A`를 나눕니다.

### 오류 수정 — 자기 수정은 흡수, 선재 버그만 분리

"오류 수정은 별도 커밋"을 그대로 적용하면 **존재하지 않았던 버그를 고치는 커밋**이
생깁니다. 브랜치 작업 중 스스로 만든 버그를 스스로 고친 경우, 앞 커밋만 체크아웃하면
실제로 깨져 있는 상태가 되고 `git log`에는 "이 기능은 버그가 있었다"는 잘못된 신호가
남습니다.

| 종류 | 판정 | 처리 |
| --- | --- | --- |
| **자기 수정** — 이 브랜치에서 만든 버그를 이 브랜치에서 고침 | 그 hunk가 건드리는 줄이 merge-base에 **없다** (파일 자체가 이 범위에서 생겼거나, 그 줄이 이 범위에서 추가됨) | 원래 기능 커밋에 **흡수** |
| **선재 버그 수정** — 베이스에 이미 있던 버그를 고침 | 그 줄이 merge-base에 **이미 존재** | 별도 `fix` 커밋으로 **분리** |

판정은 `git diff <merge-base> -- <file>`로 해당 줄의 유래를 확인합니다.

### 커밋 순서

- 기본은 **원본 이력 순서**를 따릅니다.
- `style`·`chore` 묶음은 맨 뒤에 둡니다.
- 선재 버그 수정(`fix`)은 독립적이므로 앞쪽에 두는 것을 권합니다.

### 메시지

commit-convention을 그대로 따릅니다. 이 스킬에서 특히 지킬 것:

- 형식은 `<type>: <주제> / [영역] / <세부 설명>` — 영역은 **대괄호**.
- **`<type>`을 브랜치 전체에서 고정하지 않습니다.** type이 갈리는 변경은 나누는 것이
  컨벤션입니다. 브랜치 전체에서 통일하는 것은 **주제 세그먼트**뿐입니다.
- **제목 한 줄이 기본.** body는 제목으로 담기지 않는 이유가 있을 때만 한 줄. 바꾼
  항목을 나열하지 않습니다.
- 여러 커밋을 일괄 생성하므로 매 커밋마다 확인을 받지 않고, 아래 4단계에서 계획을 한
  번에 승인받습니다.

## 실행 순서

### 1. 탐지 (한 번에 전부)

사용자에게 묻기 전에 필요한 정보를 모두 모읍니다.

```bash
git rev-parse --git-dir                                   # 저장소 확인
git branch --show-current                                 # 베이스 위에 있지 않은지
git merge-base HEAD <base>                                # 분기점
git log --oneline <mb>..HEAD                              # 되돌릴 커밋 목록
git log --oneline --merges <mb>..HEAD                     # 머지 커밋
git log --format='%an' <mb>..HEAD | sort -u               # author
git branch -r --contains HEAD                             # 원격 반영 여부
git status --porcelain                                    # 미커밋 변경
git diff --stat <mb>..HEAD                                # 변경 규모
```

- 베이스는 인자 → `origin/develop` → `develop` → `main` → `master` 순으로 존재하는
  것을 씁니다. 모호하면 승인 화면에서 확인받습니다.
- 범위 커밋이 0개면 정리할 것이 없으므로 중단합니다.
- **머지 커밋이나 내가 아닌 author의 커밋이 범위에 있으면 중단합니다.** reset이 머지를
  평탄화하면서 다른 사람의 변경을 내 커밋으로 다시 만들게 됩니다. 이때는 베이스를
  다시 지정하도록 안내합니다.

### 2. 원본 이력 스냅샷 (reset 전 필수)

reset하면 사라지는 정보를 먼저 확보합니다.

```bash
git log --reverse --name-status --format='=== %h | %s' <mb>..HEAD
git ls-files > <임시>/tracked-before.txt
```

앞의 출력이 그룹화 규칙 3(끼임 분리)과 `출처 커밋` 표기의 근거입니다. 뒤의 목록은
9단계 유실 진단용입니다.

### 3. 분할 계획 수립

「커밋 그룹화 규칙」의 판정 순서를 적용해 계획을 만듭니다. 미커밋 변경을 포함하기로
하면 그 변경도 재료에 넣고 `출처 커밋`을 `미커밋`으로 표기합니다.

### 4. 승인 (사용자 응답은 이 한 번뿐)

다음을 **한 화면에** 제시하고 승인받습니다.

- 되돌릴 커밋 목록과 범위(`<mb>..HEAD`), 변경 규모
- 경고: 원격에 올라간 브랜치면 "이후 `git push --force-with-lease`가 필요하고 공유
  브랜치라면 협업자에게 영향이 갑니다"
- 미커밋 변경이 있으면 처리 선택 — **포함**(임시 WIP 커밋으로 HEAD에 넣어 백업·검증
  범위에 포함) / **분리 보관**(`git stash -u` 후 재구성, 끝나고 `git stash pop` —
  최종 트리가 동일하므로 충돌 없이 복원됩니다) / **중단**
- **분할 계획 표**: `순서 / 커밋 메시지 / 포함 파일·hunk / 출처 커밋`

승인 전에는 어떤 변경도 만들지 않습니다.

### 5. 미커밋 변경 처리

승인에서 정한 대로 WIP 커밋 또는 stash를 수행합니다.

```bash
git add -A && git commit -m "wip: refine-commits 재구성 대상 임시 스냅샷"
```

WIP 커밋은 `<mb>..HEAD` 범위에 포함되어 재구성 시 흡수됩니다.

### 6. 백업 브랜치

reset 전에 현재 HEAD를 가리키는 백업을 만듭니다.

```bash
git branch backup/<현재-브랜치>-before-refine
```

동명 브랜치가 있으면 날짜 suffix로 피합니다. 백업 이름을 사용자에게 알립니다.

### 7. 되돌리기 (mixed reset)

```bash
git reset <merge-base>
```

`--soft`가 아닌 기본(mixed) reset을 씁니다 — 모든 변경이 워킹 트리에 unstaged로
남아 그룹별로 골라 stage하기 좋습니다. 워킹 트리 파일 내용은 그대로입니다.

reset 직후 `git status --porcelain`에 나타난 파일 목록을
`tracked-before.txt`와 대조합니다. 스냅샷에는 있는데 status에 안 보이는 파일은
**`.gitignore`에 걸린 추적 파일**입니다 — `git add`가 거부되어 조용히 유실되므로
`git add -f`로 stage합니다.

### 8. 그룹별 재커밋

승인된 계획 순서대로 stage하고 커밋합니다.

```bash
git add <그룹에 해당하는 파일들>
git commit -m "<type>: <주제> / [영역] / <세부 설명>"
```

- **한 파일이 여러 그룹에 걸치면 hunk 단위로 나눕니다.** 긴 작업에서는 예외가 아니라
  통상입니다. `git diff -- <file>`을 patch 파일로 떠서 그룹별로 쪼갠 뒤
  `git apply --cached <patch>`로 stage하는 방식을 기본으로 씁니다 — 계획서와 대조되고
  재현 가능합니다. (`git add -p`도 가능하지만 결과를 계획과 맞춰 확인하기 어렵습니다.)
- rename은 delete + add로 나타나므로 **두 경로를 함께** stage합니다.
- 그룹에 실제 변경이 없으면 `git commit`이 실패합니다 — 계획 오류이므로 중단하고
  보고합니다.
- 모든 그룹 처리 후 `git status --porcelain` **출력 전체가 비어야** 합니다(untracked
  포함). 남은 변경이 있으면 계획에서 누락된 것이므로 멈추고 보고합니다.

### 9. 결정적 검증 — 트리 동일성

```bash
git diff <backup-branch> HEAD
```

- 출력이 **비어 있어야** 합니다. 비어 있으면 재구성 전후의 코드가 완전히 동일합니다.
- 비어 있지 않으면 **내용이 바뀐 것**이므로 실패입니다. 백업을 남긴 채 중단하고
  `git reset --hard <backup-branch>`로 복구하도록 안내합니다.

### 10. 보고

```bash
git log --oneline <merge-base>..HEAD
```

- "n개 커밋 → m개 커밋으로 재구성, 트리 동일성 검증 완료"를 보고합니다.
- 백업 브랜치 이름과 삭제 명령(`git branch -D <backup>`)을 안내합니다 — **실행하지
  않습니다.**
- stash로 보관한 미커밋 변경이 있으면 `git stash pop`을 안내합니다.
- 푸시된 브랜치였다면 `git push --force-with-lease`가 필요함을 안내합니다. 푸시는
  사용자에게 맡깁니다.

---

## 주의사항

- **트리 검증은 최종 결과만 보증합니다.** hunk 단위로 쪼개면 중간 커밋에서 타입·빌드
  에러가 날 수 있습니다. 중간 커밋의 온전함이 필요하면 그룹마다 `tsc --noEmit`(또는
  해당 앱의 타입 체크)을 돌립니다.
- **머지 커밋·타 author 커밋이 범위에 있으면 실행하지 않습니다** (1단계에서 중단).
- **푸시·force-push는 이 스킬이 수행하지 않습니다.** 로컬 히스토리 정리까지만 합니다.
- 백업 브랜치는 안전장치입니다. 이 스킬은 어떤 경우에도 삭제하지 않습니다.
