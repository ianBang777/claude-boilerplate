# Commit Convention (myfair client)

현재 변경사항 전체(staged + unstaged + untracked)를 검토해, 작업 범위가 다르면
커밋을 나누고 myfair client 리포의 실제 커밋 컨벤션에 따라 커밋 메시지를
작성합니다.

## 실행 순서

1. 변경사항 전체를 파악한다.
   - `git status`로 staged·unstaged·untracked 파일을 모두 확인한다.
   - `git diff HEAD`(추적 파일)와 untracked 파일 내용까지 실제 변경을 검토한다.
2. 변경의 **목적(why)**을 파악한다. 무엇(what)은 diff가 설명한다.
   - 이번 세션의 이전 대화·작업 맥락과 조합해 각 변경이 어떤 작업에 속하는지
     판단한다.
3. **작업 범위별로 그룹핑**한다. (아래 "커밋 분리" 참고)
   - 서로 다른 작업 범위가 섞여 있으면 커밋을 나눈다. 한 작업이면 하나로 둔다.
4. 그룹마다 `git add <파일...>`로 해당 파일만 stage 하고, 아래 규칙에 따라 커밋
   메시지를 작성한다.
5. 커밋 전 사용자에게 **분리 계획과 각 커밋 메시지**를 함께 보여주고 확인을
   받는다. 승인 후 그룹 단위로 순차 커밋한다.

## 커밋 분리 (작업 범위 판단)

한 커밋은 하나의 논리 단위만 담는다. 다음 신호가 보이면 나눈다.

- 서로 다른 기능·이슈에 속하는 변경 (예: 로그인 버그 수정 + 대시보드 신규 기능)
- type이 갈리는 변경 (기능 추가 `feat` + 무관한 리팩터 `refactor`)
- 영역이 독립적인 변경 (한쪽만 되돌려도 다른 쪽이 멀쩡한 경우)

반대로, 같은 작업을 이루는 변경은 파일·영역이 여럿이어도 **하나로 묶는다**
(예: API 타입 추가 + 그 타입을 쓰는 UI). 억지로 쪼개지 않는다.

판단이 애매하면 그룹핑 초안을 사용자에게 제시하고 확인받는다.

## 커밋 메시지 형식

```
<type>: <주제> / [영역] / <세부 설명>

[body - 선택, why에 집중]
```

- 슬래시(`/`)로 세그먼트를 구분한다. `type(scope):` 형태는 쓰지 않는다.
- 첫 세그먼트는 작업 단위(기능명·작업명), 그다음 영역·세부로 좁혀 나간다.
- 세그먼트 수는 고정이 아니다. 변경 범위에 맞게 1~3개로 조절한다.

## type

| type       | 사용 시점                            |
| ---------- | ------------------------------------ |
| `feat`     | 새로운 기능 추가                     |
| `fix`      | 버그 수정                            |
| `refactor` | 기능 변경 없는 코드 개선             |
| `chore`    | 빌드, 의존성, 네이밍, 설정 변경      |
| `docs`     | 문서 변경 (계획 문서·산출물 포함)    |
| `style`    | 포맷팅 등 (로직 변경 없음)           |
| `test`     | 테스트 추가 또는 수정                |
| `perf`     | 성능 개선                            |

- 반드시 `feat`을 쓴다. `feature`·`refacotr` 같은 표기·오타는 금지.
- 실무 대부분은 `refactor` / `feat` / `fix` / `chore` / `docs`에 몰린다.

## 영역 태그 `[...]`

변경이 걸친 앱·패키지 영역을 대괄호로 표기한다.

- 주요 영역: `[myfair]`(고객), `[admin]`(어드민), `[packages]`, `[common]`,
  `[masisi]`(구 디자인 시스템), `[madix]`(신 디자인 시스템), `[scripts]`
- 복수 영역은 가운데점(`·`)으로 연결: `[packages·admin·myfair]`, `[myfair·api]`
- 영역이 주제만으로 자명하면 태그를 생략해도 된다.

## 주제 · 세부 (subject)

- 한국어 **명사구**로 쓴다. "추가", "수정", "제거", "이관", "교체" 등 동작 명사로
  끝맺는다. (명령형 동사문 아님)
- 끝에 마침표를 붙이지 않는다.
- 글자 수 상한은 두지 않는다. 무엇이 왜 바뀌는지 드러나면 길어도 된다.

## body (선택)

- 복잡한 변경은 **왜** 그렇게 했는지를 본문에 남긴다. 무엇이 바뀌었는지는 diff가
  말한다.
- 변경 항목이 여러 개면 `-` 불릿으로 나열한다.

## 예시

```
feat: 수출바우처 예산표 버전 비교 / [myfair/export-voucher] / 고객 페이지 섹션 재배치 + 버전 Select 교체

Figma 기준 섹션 순서 정렬 및 버전 선택 UI를 디자인 시스템으로 교체.
- 버전 Select을 표 상단 타이틀 우측으로 인라인 이동
- MasisiNativeSelect → MadixSelect
```

```
refactor: 전체 참가 업무 / [myfair] / 부가 서비스 테이블 행 정렬 (피그마 순서·접수 우선·종료 후순위)
```

```
fix: 현장정보 일정 null 크래시 / [myfair·api] / schedule 응답 nullable화 + 모바일 템플릿 옵셔널 체이닝
```

```
chore: 부스 데코 인보이스 다건화 / [packages·admin·myfair] / 구 단건 인보이스 경로 제거
```
