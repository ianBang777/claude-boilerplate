# 03. 테스트 주도 개발 (TDD)

## Red → Green → Refactor

1. **Red**: 실패하는 테스트를 먼저 쓴다. (원하는 동작을 코드로 명세)
2. **Green**: 테스트를 통과시키는 **최소한**의 코드를 쓴다.
3. **Refactor**: 테스트를 초록으로 유지한 채 구조를 정리한다.

작은 단위로 빠르게 순환한다. 한 번에 하나의 동작만.

## 좋은 테스트 (F.I.R.S.T)

- **Fast**: 빠르게 — 자주 돌릴 수 있어야 한다.
- **Independent**: 독립적 — 테스트 간 순서 · 상태 의존 금지.
- **Repeatable**: 반복 가능 — 환경과 무관하게 같은 결과.
- **Self-validating**: 통과/실패가 자동 판정된다.
- **Timely**: 적시 — 구현 직전/직후에 작성.

## 무엇을 테스트하나

- **"어떻게 만들었는지"가 아니라 "무엇을 하는지"** 를 테스트한다. → 입력을
  넣으면 어떤 결과/동작이 나오는지(겉으로 약속한 것)만 검증한다. → 내부
  구현(어떤 함수를 몇 번 부르는지 등)은 테스트하지 않는다.
- 경계값 · 예외 상황 · 실패 케이스를 우선 다룬다.
- 한 테스트는 하나만 검증한다 (준비 → 실행 → 확인, Act는 한 줄).
- 내부 구현을 바꿔도(리팩터링) 테스트는 안 깨져야 한다. 깨진다면 너무 세부에
  묶인 것.

**우선 대상**: 복잡 · 중요한 도메인 로직, 알고리즘(계산 · 변환 · 검증).
**비대상**: 단순 CRUD(DB · API 호출만), getter/setter, 프레임워크 코드.

## 테스트 스타일 우선순위

1. **출력 기반**: 입력 → 출력 (부작용 없음). 가장 견고하다.
2. **상태 기반**: 실행 후 객체 · 시스템 상태를 확인한다.
3. **통신 기반**: Mock 호출을 검증한다. 비관리 의존성에 한해 최후 수단.

## 의존성 다루기

- **관리 의존성**(도메인 모델 · 서비스 등 내부 객체)은 **실제 객체**를 쓴다.
  Mock하면 정작 검증해야 할 로직이 빠진다.
- **비관리 의존성**(DB · 외부 API · 메시지 큐 · SMTP 등 외부 시스템)만 Mock한다.
- 복잡한 로직과 I/O를 분리(험블 객체)하면 로직은 단위 테스트, I/O는 통합
  테스트로 자연히 나뉜다.

## 단위 vs 통합

- **단위**: 도메인 · 알고리즘. 격리 · 빠름. 비관리 의존성만 Mock.
- **통합**: 외부 시스템과의 상호작용. 실제 DB · API. 느리지만 신뢰도 높다.

## 실용 지침

- 모든 코드에 TDD를 강요하지 않는다. 로직이 불확실 · 복잡 · 회귀 위험이 클 때
  가장 효과적.
- 버그 수정 시: 먼저 그 버그를 재현하는 실패 테스트를 쓰고, 그다음 고친다.
- 모킹은 비관리 의존성에 한정한다 (위 "의존성 다루기" 참고). 과한 모킹은 피한다.
- 커버리지 숫자가 목표가 아니다. **신뢰**가 목표다.
